Why this graph looks the way it does

An earlier draft of the source doc cited crypto_aes_ctx / aes_expandkey() in crypto/aes_generic.c as the generic AES key-schedule path. That file no longer exists — a 2026 kernel restructuring ("crypto: aes — Replace aes-generic with wrapper around lib") replaced it with crypto/aes.c, a thin wrapper backed by a new lib/crypto/aes.c. As a direct result, xts(aes) is registered three separate times in the current kernel, ranked by cra_priority, and crypto_alloc_skcipher() picks whichever is highest and available. Every layer below branches three ways for exactly this reason.

Dotted arrows mark conditional/priority-based selection. Solid arrows are unconditional function calls. Amber nodes are structurally confirmed but carry at least one unverified edge — most importantly, the lskcipher-to-skcipher adaptation shim that lets the generic crypto/xts.c template obtain a handle to ecb(aes) now that crypto/ecb.c registers it as an lskcipher, not a skcipher.

What changed from the three-step summary

The prose version of this material in the source doc collapses to three steps: create the cipher object, key it once, use it on every sector. That's still true — but each step branches on which of three real kernel implementations of xts(aes) wins selection.

  1. tfm creation is unconditional — one call, one function, regardless of backend.
  2. Backend selection happens once per volume, driven by cra_priority: AES-NI (401) beats the AES library wrapper (110) beats the legacy template composition (uncertain, lower). Whichever wins determines every function called downstream.
  3. Keying still runs exactly once per unlock (crypto_skcipher_setkey() — confirmed to appear exactly once in the whole of dm-crypt.c), but through a different call chain and into a different struct depending on the backend from step 2.
  4. Per-sector encrypt/decrypt is what actually runs continuously — the diagram makes explicit that crypto_skcipher_encrypt()/decrypt() don't touch the key schedule directly; they dispatch to a backend-specific routine several calls deeper that does.
  5. Teardown zeroes the key material twice, independently: once when the tfm is freed (crypto_free_skcipher() — documented in its own comment as "zeroize and free cipher handle"), once when struct crypt_config itself is freed.

Scope

This diagram covers only the master key's kernel-side lifecycle. Two related diagrams are planned as separate work, not yet built: tweak/IV generation (iv_gen_ops, crypt_iv_essiv, referenced by the bio-dispatch layer above but not traced here), and the full userspace-to-kernel unlock path (keyslot unwrap, AF-merge, digest verification, the luksOpen handoff into the graph above). Don't read this page as covering either.
